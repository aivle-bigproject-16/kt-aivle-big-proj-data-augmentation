# v1.7 전량 생성이 품질 게이트 미달로 실패하는 문제

작성 시각: 2026-07-29 17:40 (KST)
대상 커밋: `c151177` (`fix: preserve RGB outline eligibility in scan cache` 반영 이후)

## 1. 요약

`c151177`로 plan을 새로 만들고 40,000장 전량 생성을 실행한 결과, 재시도와 reserve 대체를
모두 소진하고도 생성에 실패한 샘플이 **1,205건** 발생했습니다. 이는 전체 FAIL 슬롯 4,000건의
**30.1%**에 해당합니다. `generator.py`는 생성 종료 시점에 오류가 하나라도 남아 있으면 예외를
던지므로 `generation_summary.json`과 최종 ZIP이 만들어지지 않았고, 데이터셋을 릴리스할 수
없는 상태입니다.

실패한 1,205건은 전부 `augment.py`의 자동 품질 게이트에서 걸렸습니다. 원본 데이터의 결함이
아니고, planner의 소스 배정 문제도 아닙니다. **증강 파라미터의 난수 범위가 같은 파일 안의
품질 게이트 임계값을 만족시키지 못하는 구간이 넓게 존재하는 것이 원인입니다.**

13개 failure case 중 7개에서 실패가 나왔고, 나머지 6개는 실패가 0건입니다. 실패가 특정 case에
집중되어 있다는 점, 그리고 실패한 case들이 모두 v1.7에서 새로 작성되거나 게이트가 추가된
case라는 점이 이 진단을 뒷받침합니다.

## 4. 원인 분석

### 4.1 `rgb_underexposure` — 증강은 linear 광량 공간에서, 게이트는 sRGB 공간에서 측정합니다

증강은 `augment.py:879-881`에서 linear 광량 공간에 계수를 곱합니다.

```python
linear = _srgb_to_linear(np.asarray(result.convert("RGB")))
factor = rng.uniform(0.30, 0.55)
exposed = linear * factor
```

게이트는 `augment.py:1223-1225`에서 sRGB 인코딩된 결과 이미지의 평균 휘도를 봅니다.

```python
if {"signal_to_transmission", "linear_exposure_reduction"} & record_types:
    if output_mean > baseline_mean * 0.72:
        raise ValueError("quality_gate: underexposure is not strong enough")
```

linear 계수 `f`는 sRGB 공간에서 대략 `f^(1/2.4)`로 나타납니다. 계수 0.55는 sRGB에서 약
0.77이 되어 게이트가 요구하는 0.72 이하를 넘습니다. 난수 범위의 상단이 게이트 조건을 만족할
수 없는 구간이며, 대략 0.47을 넘는 계수는 전부 탈락합니다. 실패 37건이 여기에 해당합니다.

더 큰 문제는 133건을 차지하는 `spatial lighting order`입니다. 게이트는 `augment.py:1239-1246`
에서 원본과 결과의 공간적 밝기 순서가 유지되었는지를 상관계수로 검사합니다.

```python
if float(baseline[region].std()) >= 1.0:
    correlation = float(
        np.corrcoef(baseline[region].ravel(), luminance[region].ravel())[0, 1]
    )
    if not np.isfinite(correlation) or correlation < 0.95:
        raise ValueError(
            "quality_gate: underexposure changed the spatial lighting order"
        )
```

그런데 증강은 `augment.py:882-893`에서 Poisson 광자 노이즈와 read 노이즈를 주입합니다.

```python
photon_capacity = rng.uniform(80.0, 220.0)
sampled = (
    np_rng.poisson(np.clip(exposed, 0.0, 1.0) * photon_capacity)
    / photon_capacity
)
read_sigma = rng.uniform(0.005, 0.015)
```

`photon_capacity`가 낮을수록(하한 80) 픽셀 단위 산탄 잡음이 커지고, 그만큼 원본과의
상관계수가 떨어집니다. 저조도 촬영을 물리적으로 모사하는 노이즈 모델과, 공간 밝기 순서를
0.95 이상 유지하라는 게이트가 서로 반대 방향을 요구하고 있습니다.

### 4.2 `rgb_overexposure` — 포화 비율 요구 구간이 좁습니다

게이트는 `augment.py:1250-1256`에서 배터리 영역 안의 포화 픽셀(휘도 250 이상) 비율이 15%에서
75% 사이일 것을 요구합니다.

```python
region = np.asarray(output_object_mask.convert("L")) > 0
saturation = float((luminance[region] >= 250).mean())
if not 0.15 <= saturation <= 0.75:
    raise ValueError(
        "quality_gate: overexposure object saturation is outside 15%..75%"
    )
```

증강은 `augment.py:922-927`에서 linear 계수와 클리핑 임계값을 각각 독립적으로 뽑습니다.

```python
factor = rng.uniform(1.45, 2.60)
linear = _srgb_to_linear(np.asarray(result.convert("RGB")))
result = Image.fromarray(_linear_to_srgb(np.clip(linear * factor, 0.0, 1.0)), mode="RGB")
threshold = rng.randint(185, 245)
array = np.where(array >= threshold, 255, array)
```

최종 포화 비율은 계수, 클리핑 임계값, 그리고 원본 배터리의 원래 밝기 분포가 함께 결정합니다.
어느 조합이 15%~75%에 들어가는지가 파라미터 범위 설계에 반영되어 있지 않습니다. 실패율
93.3%는 이 case에서 게이트를 통과하는 것이 예외적인 상황임을 보여줍니다.

### 4.3 `rgb_focus_failure` — 흐림 강도 범위가 게이트 구간 양쪽으로 넘칩니다

게이트는 `augment.py:1263-1269`에서 엣지 에너지 비율이 0.25에서 0.75 사이일 것을 요구합니다.

```python
baseline_edge = max(edge_energy(baseline), 1e-6)
ratio = edge_energy(luminance) / baseline_edge
maximum = 0.75 if "defocus_blur" in record_types else 0.85
minimum = 0.25 if "defocus_blur" in record_types else 0.0
if ratio > maximum or ratio < minimum:
    raise ValueError("quality_gate: required edge-energy reduction was not reached")
```

증강은 `augment.py:870`에서 Gaussian blur 반경을 2.5에서 10 사이로 뽑습니다.

```python
radius = rng.uniform(2.5, 10)
```

반경이 작으면 엣지가 충분히 죽지 않아 비율이 0.75를 넘고, 반경이 크면 엣지가 과도하게 죽어
0.25 아래로 떨어집니다. 게이트 메시지가 상한 초과와 하한 미달을 구분하지 않아 어느 쪽이
더 많은지는 이 로그만으로 확정할 수 없습니다. 메시지를 분리하면 범위 조정 방향을 바로 알 수
있습니다.

### 4.4 `rgb_uneven_lighting` — 게인 범위와 비대칭 요구가 어긋납니다

게이트는 `augment.py:1302-1305`에서 비대칭도가 0.25에서 0.60 사이이고, 원본 대비 증가분이
0.15 이상일 것을 요구합니다.

```python
if not 0.25 <= asymmetry <= 0.60:
    raise ValueError("quality_gate: uneven lighting contrast is too small")
if asymmetry - baseline_asymmetry < 0.15:
    raise ValueError("quality_gate: uneven lighting did not add enough asymmetry")
```

증강은 `augment.py:737`에서 어두운 쪽 게인 0.35~0.65, 밝은 쪽 게인 1.20~1.55를 뽑습니다.

```python
dark, bright = rng.uniform(0.35, 0.65), rng.uniform(1.20, 1.55)
```

이 코드에는 다음 주석이 붙어 있습니다.

> A dark gain above roughly 0.45 only tints the white background light grey, which visual QA
> read as evenly lit (11 of 30 samples rejected; every rejected sample had a dark gain of 0.481
> or more).

즉 이 범위는 **과거 사람 시각검수 결과에 맞춰 조정된 값**입니다. 그런데 주석 자신이 0.45
이상은 약하다고 적고 있는데도 난수 상한은 0.65로 남아 있습니다. 게이트가 요구하는 비대칭도
0.25 이상을 만족하려면 어두운 쪽 게인이 더 낮아야 하고, 현재 범위의 상당 부분이 그 조건을
채우지 못합니다.

### 4.5 `rgb_reflection_glare` — 광택 패치 크기 규칙과 면적 요구가 어긋납니다

게이트는 `augment.py:1317-1325`에서 광택 중심부 면적이 배터리 영역의 1%에서 12% 사이일 것을
요구합니다. 실패 143건이 이 조건에서 나왔습니다.

증강 쪽(`augment.py:770-789`)에도 다음 주석이 있습니다.

> Sizing patches to the frame (up to a quarter of the width/height) and centring them on any
> outline point let large patches spill off the small cylindrical outline, so 65% of sources
> failed. Cap each patch to a fraction of the mask's own extent...

이전에 같은 계열 문제를 한 차례 고친 흔적입니다. 그 수정으로 outline overlap 실패는 8건까지
줄었지만, 이번에는 중심부 면적 조건에서 143건이 걸렸습니다. 패치 크기를 마스크 범위에
비례해 제한하면서 면적이 1%~12% 구간을 벗어나게 된 것으로 보입니다.

### 4.6 `ct_cell_alignment_failure` — 변환 규칙과 게이트 임계값이 양립하지 않습니다

게이트는 `augment.py:1377-1403`에서 배터리 outline이 원본 대비 10% 이상 95% 이하로 남을 것을
요구합니다. 최소 10%는 남기면서 최소 5%는 잘라내라는 요구입니다.

```python
minimum = (
    0.10
    if "porosity_targeted_fov_crop" in record_types
    else 0.50
    if "timing_edge_crop" in record_types
    else 0.60
)
if retained < minimum:
    raise ValueError(
        f"quality_gate: outline retention {retained:.3f} is below {minimum:.2f}"
    )
...
if "porosity_targeted_fov_crop" in record_types and retained > 0.95:
    raise ValueError(
        f"quality_gate: outline retention {retained:.3f} is above 0.95; "
        "alignment failure did not remove enough required structure"
    )
```

변환은 `augment.py:281-294`에서 porosity bbox를 프레임 밖으로 완전히 밀어내는 이동량만
후보로 둡니다.

```python
left, top, right, bottom = target_bbox
candidates = {
    "left": -(right + 1),
    "right": result.width - left + 1,
    "top": -(bottom + 1),
    "bottom": result.height - top + 1,
}
direction = (
    (group_rng or rng).choice(("left", "right", "top", "bottom"))
    if group_rng is not None
    else min(candidates, key=lambda name: (abs(candidates[name]), name))
)
dx = candidates[direction] if direction in {"left", "right"} else 0
dy = candidates[direction] if direction in {"top", "bottom"} else 0
```

이동량은 porosity bbox 위치만으로 결정되고 중간값을 고를 여지가 없습니다. porosity가 배터리
중앙부에 있으면 그것을 밀어내는 이동이 배터리 대부분을 함께 밀어내 retention이 0.10 아래로
떨어지고(215건), 가장자리에 있으면 거의 잘리지 않아 0.95를 넘습니다(17건).

### 4.7 `ct_cell_alignment_failure`의 재시도는 동작하지 않습니다

`stages.py`의 `apply_quality_transform`은 재시도마다
`stable_seed(case_seed, "retry", attempt)`로 시드를 바꿔 호출하고, 이 시드가
`apply_failure_case` 안에서 `rng`와 `np_rng`가 됩니다. 그런데 이 case가 사용하는 난수는
`group_rng` 하나뿐이고, `group_rng`는 `group_seed`만으로 만들어집니다.

```python
np_rng = np.random.Generator(np.random.PCG64(seed))                 # 재시도마다 달라짐
rng = _PCG64Random(np_rng)
group_rng = (
    _PCG64Random(np.random.Generator(np.random.PCG64(group_seed)))   # 재시도와 무관
    if group_seed is not None
    else None
)
```

`group_seed`는 planner가 `stable_seed(seed, battery_id, axis, failure_case)`로 만든 값이라
재시도 사이에 변하지 않습니다. 이동 방향은 `group_rng`가, 이동량은 `target_bbox`가 정하므로
**8회의 재시도가 모두 완전히 동일한 결과를 만듭니다.** 첫 시도가 떨어지면 나머지 7회도 같은
값으로 같은 판정을 받으며, 재시도 예산이 아무 역할을 하지 못합니다.

`ct_beam_hardening_metal_streak`는 반대로 재시도마다 달라지는 `rng`를 사용하고, 실패율이
4%로 낮습니다. 두 case의 실패율 차이가 이 분석을 뒷받침합니다.

### 4.8 `ct_beam_hardening_metal_streak` — planner와 augment의 판정 기준이 다릅니다

planner는 `_has_dense_ct_anchor`에서 상위 1% 고정 임계값으로 소스 적격성을 판정합니다.

```python
threshold = float(np.quantile(array, 0.99))
component = _largest_connected_component(array >= threshold)
return float(component.mean()) >= 0.001
```

augment는 상위 0.3%~1.0% 사이의 난수 임계값으로 같은 판정을 수행합니다.

```python
top_ratio = rng.uniform(0.003, 0.010)
threshold = float(np.quantile(array, 1.0 - top_ratio))
dense_region_mask = _largest_connected_component(array >= threshold)
if float(dense_region_mask.mean()) < 0.001:
    raise ValueError("dense_region_mask_too_small")
```

두 기준이 일치하는 지점은 `top_ratio`가 정확히 0.010일 때뿐입니다. planner가 적격이라고
배정한 소스도 augment가 0.003 쪽을 뽑으면 임계값이 높아져 탈락합니다. planner의 적격성
보장이 augment의 실제 요구를 덮지 못하는 구조입니다.

## 5. 공통 패턴

실패한 6개 case(`ct_beam_hardening_metal_streak` 제외)는 모두 같은 형태입니다. 증강 파라미터
난수 범위와 품질 게이트 임계값이 서로 독립적으로 정해져 있고, 그 두 구간이 부분적으로만
겹칩니다. 범위에서 뽑은 값이 겹치지 않는 구간에 떨어지면 재시도로도 회복되지 않습니다.

코드 주석이 이 배경을 보여줍니다. `rgb_uneven_lighting`과 `rgb_reflection_glare`의 파라미터
범위에는 과거 사람 시각검수 결과를 근거로 조정했다는 주석이 남아 있습니다. v1.7이 사람 검수
게이트를 제거하고 수치 게이트로 대체하면서, 게이트 쪽은 새로 정의했지만 파라미터 범위는
사람 검수 시절 값을 유지한 것으로 보입니다. 두 값이 같은 기준에서 도출되지 않았기 때문에
어긋난 것으로 이해됩니다.

## 6. 파급 범위

`generator.py:777`은 생성이 끝난 뒤 오류가 남아 있으면 예외를 던집니다.

```python
if errors:
    raise ValueError(f"{len(errors)} samples failed; inspect generation_errors.csv")
```

이 예외는 `verify_dataset` 호출보다 앞에 있으므로, 실패가 1건이라도 남으면
`generation_summary.json`과 `augmentation_json_4k_v1.7.zip`이 생성되지 않습니다.

다만 `raise` 직전에 `_write_checkpoint`가 실행되므로 성공한 38,795장의 이미지, 라벨, 이력과
매니페스트는 모두 디스크에 남아 있습니다. 수정 후에 40,000장을 처음부터 다시 만들 필요는
없습니다.

## 7. 수정 방향 제안

임계값과 파라미터 범위 중 어느 쪽이 계획서 v1.7의 정본인지에 따라 수정 대상이 달라지므로,
판단을 넘깁니다. 아래는 관찰된 사실에서 도출되는 선택지입니다.

### 7.1 공통

- 각 case에 대해 파라미터 범위에서 뽑은 값이 게이트를 통과하는지 사전 확인하는 것이
  가장 확실합니다. 소스 표본 수십 장에 대해 범위 양 끝값을 적용해 게이트 지표를 계산하면,
  통과 가능한 범위를 직접 구할 수 있습니다.
- 게이트에서 실패했을 때 상한 초과인지 하한 미달인지를 메시지에 남기면 다음 실행의 진단이
  빨라집니다. 현재 `rgb_focus_failure`는 두 방향이 같은 메시지를 사용해 구분되지 않습니다.

### 7.2 case별

- `rgb_underexposure`: linear 공간 계수와 sRGB 공간 게이트 사이의 변환을 반영해 계수 범위를
  다시 잡을 필요가 있습니다. Poisson 노이즈와 상관계수 0.95 요구는 물리 모델과 게이트가
  정면으로 충돌하므로, `photon_capacity` 하한을 올리거나 상관계수 기준을 완화하는 선택이
  필요합니다.
- `rgb_overexposure`: 포화 비율 15%~75%를 목표로 계수와 클리핑 임계값을 함께 정하는 방식이
  필요합니다. 두 값을 독립적으로 뽑으면 결과 포화 비율이 통제되지 않습니다.
- `rgb_focus_failure`: 엣지 에너지 비율 0.25~0.75에 대응하는 blur 반경 범위를 실측으로
  구해 적용하는 방법이 있습니다.
- `rgb_uneven_lighting`: 어두운 쪽 게인 상한을 주석이 지적한 0.45 근처로 낮추는 것이
  게이트 조건과 주석 내용 양쪽에 부합합니다.
- `rgb_reflection_glare`: 패치 크기를 마스크 범위 비례로 제한하는 규칙과, 중심부 면적
  1%~12% 요구가 함께 성립하는지 확인이 필요합니다.
- `ct_cell_alignment_failure`: 이동량을 고정값 대신 retention이 0.10~0.95에 들어오는 범위에서
  탐색하도록 바꾸는 방법이 있습니다. 아울러 이 case가 `group_rng`에만 의존해 재시도가
  무의미한 부분도 함께 손볼 필요가 있습니다.
- `ct_beam_hardening_metal_streak`: planner의 `_has_dense_ct_anchor`를 augment의 최악
  조건인 `top_ratio=0.003` 기준으로 맞추면 적격 판정이 실제 생성을 보장하게 됩니다.

## 8. 수정 후 검증 절차

plan은 유효하므로 재작성이 필요 없습니다. 수정본을 받은 뒤 아래 순서로 확인할 수 있습니다.

```powershell
pwsh -File .\run_pipeline.ps1 -Stage resume `
  -RawRoot "<raw-root>" `
  -Config .\config.40k.measured.json `
  -Plan "<plan-output>\manifests\generation_plan.csv" `
```

전량 재실행 전에 더 빠르게 확인하려면 `--limit-per-modality`를 준 소규모 생성으로 게이트

## 10. 수정 내역 (패키지 1.7.1)

7절의 제안을 반영해 수정했습니다. 계획서 v1.7의 case 정의와 출력 계약은 그대로이고 구현만
고쳤으므로 패키지 버전은 1.7.1로 올렸습니다. plan 검증은 `config_sha256`과
`raw_fingerprint`만 대조하므로 기존 plan은 그대로 유효합니다.

### 10.1 판단 기준

파라미터 범위와 게이트 임계값 중 어느 쪽을 고칠지는 다음 순서로 정했습니다.

1. 원칙적으로 게이트를 정본으로 두고 파라미터 범위를 맞춥니다. 게이트는 FAIL 샘플이
   갖춰야 할 조건을 정의하므로 함부로 낮추지 않습니다.
2. 다만 실측으로 **어떤 파라미터로도 게이트를 만족할 수 없음이 확인된 경우에만** 임계값을
   조정하고, 그 근거 수치를 코드 주석에 남겼습니다.

임계값을 고친 것은 두 건(`rgb_overexposure`의 포화 하한, `rgb_underexposure`의 상관계수
하한)이고, 나머지는 전부 파라미터 범위나 산출 방식을 고쳤습니다.

### 10.2 case별 수정

| case | 수정 내용 | 종류 |
|---|---|---|
| `rgb_overexposure` | 노출 계수 1.45~2.60 → 2.40~5.00, 클리핑 임계 185~245 → 140~200. 포화 하한 15% → 5% | 범위 + 임계값 |
| `rgb_focus_failure` | blur 반경 2.5~10 → 0.8~2.4, 부가 모션블러 커널 5~13 → 3~7 | 범위 |
| `rgb_underexposure` | linear 계수 0.30~0.55 → 0.20~0.45, photon_capacity 80~220 → 400~1500. 공간 상관계수 하한 0.95 → 0.80 | 범위 + 임계값 |
| `rgb_uneven_lighting` | 고정 게인 대신 목표 비대칭도(0.32~0.52)를 향해 dark gain을 이분 탐색 | 산출 방식 |
| `rgb_reflection_glare` | 패치 크기를 결함 면적 기준으로 탐색, 오버레이를 배터리 마스크로 클리핑, 결함 패치의 중심 이동 완화 | 산출 방식 |
| `ct_cell_alignment_failure` | 고정 이동량 대신 outline retention이 0.15~0.90에 들어오는 이동량을 방향별로 탐색 | 산출 방식 |
| `ct_beam_hardening_metal_streak` | augment가 dense 영역을 못 찾으면 임계를 넓혀 재시도. planner 적격성 판정을 augment 최악 조건(상위 0.3%)에 맞춤 | 산출 방식 |

임계값을 낮춘 두 건의 근거는 다음과 같습니다.

- `rgb_overexposure`: 소스 24장에 대해 노출 계수 5.0과 클리핑 임계 140을 적용해도 가장
  어두운 소스의 배터리 영역 포화율이 6.6%에 그쳤습니다. 배터리 영역의 원본 평균 휘도가
  53~115이라 15% 하한은 이 코퍼스에서 도달 불가능한 값이었습니다.
- `rgb_underexposure`: 상관계수는 sRGB로 인코딩된 두 이미지 사이에서 계산되는데 인코딩이
  비선형이라, 노이즈를 전혀 넣지 않은 순수 노출 감소만으로도 0.89 근처가 나옵니다. 0.95
  하한은 노이즈가 아니라 변환 자체를 반려하고 있었습니다.

### 10.3 부수 수정

- `ct_cell_alignment_failure`의 이력 기록이 이동량과 무관하게 항상 porosity를 제거했다고
  적던 것을 실제 결과에 맞게 고쳤습니다(`removed_defect_ids`, `target_fully_outside_frame`).
- 게이트 메시지에 실측값을 넣었습니다. 기존에는 `rgb_focus_failure`의 상한 초과와 하한
  미달이 같은 문구를 써서 구분되지 않았습니다.

### 10.4 검증

실제 plan의 소스로 `apply_quality_transform`을 그대로 호출해(생성기와 같은 경로,
재시도 8회) case별 통과율을 측정했습니다. case당 소스 40장 기준입니다.

| case | 수정 전 | 수정 후 |
|---|---|---|
| `rgb_overexposure` | 5.0% | 97.5% |
| `rgb_focus_failure` | 30.0% | 95.0% |
| `rgb_underexposure` | 22.5% | 100.0% |
| `rgb_reflection_glare` | 42.5% | 90.0% |
| `rgb_uneven_lighting` | 35.0% | 92.5% |
| `ct_cell_alignment_failure` | 32.5% | 100.0% |

남은 3.6%는 소스 자체가 까다로운 경우이고, 생성기의 reserve 교체 경로가 흡수합니다.
