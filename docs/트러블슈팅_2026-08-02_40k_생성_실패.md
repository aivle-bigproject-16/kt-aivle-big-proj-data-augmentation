## 1. 경로 하드코딩과 `.env` 도입

다른 머신에서는 명령마다 네 개의 경로를 손으로 넘겨야 했다.

저장소 루트의 `.env`에서 기본값을 읽도록 바꿨다. 우선순위는 CLI 인자, 셸 환경변수,
`.env` 순이다. `run_pipeline.ps1`도 같은 파일을 읽는다.

| 변수 | 채우는 인자 |
|---|---|
| `QFA_RAW_ROOT` | `--raw-root` |

| `QFA_SMOKE_DIR` | smoke 생성의 `--output` |

구현에서 두 가지를 의도적으로 정했다.

**값에 이스케이프 처리를 하지 않는다.** Windows 경로 `C:\Users\new`의 `\n`이 개행으로

**상대경로는 실행한 폴더가 아니라 `.env` 파일이 있는 폴더 기준으로 푼다.**
`QFA_CONFIG=./config.40k.json`이 어느 폴더에서 실행하든 같은 파일을 가리켜야 한다.

`run_pipeline.ps1`은 pwsh 7 버전 확인을 `-Detached` 분기보다 **앞으로** 옮겼다.
종전에는 Windows PowerShell 5.1로 실행해도 부모가 분리 실행에 성공하고 자식만
죽었다. `.env`에 한글 경로가 들어가면서 5.1의 ANSI 오독이 더 치명적이 됐다.

## 2. `effective_jobs`가 1로 떨어지는 문제

smoke summary에 `requested_jobs: 8`인데 `effective_jobs: 1`이 찍혔다.

원인은 `generator.py:513`이다.

```python
requested = max(1, int(config.get("jobs", 1)))
measured_worker_bytes = config.get("worker_peak_rss_bytes")
if requested > 1 and not measured_worker_bytes:
    return 1
```

`config.40k.json`에는 `worker_peak_rss_bytes`가 없다. 이 키가 없으면 요청 잡 수와
무관하게 1잡으로 강제된다. 설계상 의도된 안전장치이고, smoke가 실측치를 뽑아
`<config>.measured.json`을 만드는 것이 정상 흐름이다(`run_pipeline.ps1`의
`Write-MeasuredConfig`).

CLI를 직접 호출하면 이 단계가 빠진다. 그대로 전체를 돌렸다면 1.28 sample/초로
40,000장에 약 8.7시간이 걸렸을 것이다.

smoke 실측값 `worker_peak_rss_bytes = 1,585,131,520`(1.48 GiB)을 넣어
`config.40k.measured.json`을 만들고 다시 돌렸다.

| 구분 | 처리량 | 40,000장 환산 |
|---|---|---|
| measured 없음 (1잡) | 1.28 sample/초 | 약 8.7시간 |
| measured 적용 (6잡) | 8.59 sample/초 | 약 78분 |

**6.7배** 차이다. plan을 다시 만들 필요는 없다. `worker_peak_rss_bytes`는
`planner.PERFORMANCE_ONLY_KEYS`에 있어 plan 해시 재료에서 빠지며, 두 config의
`_config_hash()`가 같은 것을 확인했다.

주의할 점은 smoke가 단일 프로세스로 돌기 때문에 측정된 1.48 GiB에 부모 프로세스
오버헤드가 섞여 있다는 것이다. 워커당 실사용은 이보다 작다. 잡 수를 과소 추정하는
쪽이므로 안전한 방향이지만, 정확한 값은 아니다.

## 3. generate 중단 — RGB 증강 실패 548건

98.58%에서 다음으로 중단됐다(`generator.py:777`).

```text
ValueError: 548 samples failed; inspect generation_errors.csv
```

### 실패 분포

`generation_errors.csv` 548행을 집계했다. **전부 RGB이고 전부 `attempt=8`이다.**
8은 `max_augmentation_retries` 상한이므로 재시도를 모두 소진했다는 뜻이다.

| 오류 | 건수 | 해당 case | 생성/목표 |
|---|---:|---|---|
| `glare_no_gate_safe_geometry` | 472 | `rgb_reflection_glare` | 946 / 1,418 |
| `uneven_lighting_no_gate_safe_gradient` | 64 | `rgb_uneven_lighting` | 1,354 / 1,418 |
| `quality_gate: underexposure outline luminance ratio` | 12 | `rgb_underexposure` | 1,405 / 1,417 |

`rgb_reflection_glare`가 86%를 차지한다. 목표의 67%만 생성됐으니 약 1/3이 영구
실패한 것이고, 산발적 불운이 아니라 구조적 문제다.

### reserve는 동작했지만 모자랐다

`reserve_sources.csv`는 모달리티당 500개다. `lineage_private.csv`의
`raw_image_path`와 대조한 결과 **reserve 소스 295개가 실제 산출물에 들어갔다.**
대체 기능 자체는 정상이다. 다만 RGB 실패가 548건이라 500개 풀로는 메울 수 없었다.

### 재시도 8회가 무의미하다

이것이 핵심이다. `stages.py:186`의 재시도 루프는 **시드만 바꾼다.**

```python
for attempt in range(max_retries):
    result = apply_failure_case(..., stable_seed(case_seed, "retry", attempt), ...)
```

그런데 glare의 기하 탐색(`augment.py:1096-1177`)은 후보 격자를 시드와 무관하게
만든다. 축은 object 마스크의 주성분에서, 길이·폭 계수는 상수 튜플
(`length_factors = (0.50, 0.65, 0.80)`, `width_factors = (1.0, 1.25, 1.50)`)에서
온다. 루프 안에서 `rng`를 쓰는 곳은 알파값 하나뿐이고, 그 값은 `alpha > 0` 판정에
영향을 주지 않는다. 기준점 `base_x, base_y`도 defect가 있으면 defect 중심으로
고정된다(`rng.choice`는 defect가 없을 때만 탄다).

실패 소스 25건에 대해 서로 다른 시드 8개로 `apply_failure_case`를 직접 호출해
확인했다. **25건 모두 8회가 완전히 동일한 예외를 냈다.**

즉 이 실패 모드에서 `max_augmentation_retries`를 늘리는 것은 아무 효과가 없다.
같은 계산을 더 반복할 뿐이다.

### 후보가 기각되는 지점

실패 소스 25건의 후보 탐색을 재현해 기각 사유를 셌다(후보 900개).

| 기각 사유 | 건수 | 비중 |
|---|---:|---:|
| `defect_coverage` 범위 밖 | 524 | 58% |
| `core_ratio < 0.045` | 357 | 40% |
| └ 그중 outline 밖으로 20% 이상 잘려서 | 342 | (357의 96%) |
| `core_ratio > 0.12` | 19 | 2% |

25건 전부 통과 후보가 **0개**였다.

제약은 세 개가 동시에 걸린다.

- 종횡비 `(2 * half_length) / width >= 5.0` — 얇고 긴 선이어야 한다
- `0.045 <= core_ratio <= 0.12` — 코어 면적이 object의 4.5~12%
- `minimum_defect_coverage <= defect_coverage <= 0.70`

`minimum_defect_coverage`는 `min(0.45, 0.085 / (defect/object))`이다.
defect가 object에 비해 작으면 0.45가 걸리므로, **object의 7.5% 남짓인 얇은 선 두 개로
defect 면적의 45%를 덮어야 한다.**

`core_ratio < 0.045`로 기각된 357건 중 342건(96%)은 그린 선이 object outline 밖으로
잘려나가서 발생했다(`candidate_array[~object_array] = 0`). 선을 object 주축 방향으로
길게 그리는데 RGB 원통 셀은 폭이 좁아 상당 부분이 마스크 밖으로 나간다.

### 성공 소스와 무엇이 다른가

성공·실패 각 30~40건의 소스 마스크를 비교했다. 처음 세운 가설 두 개는 **틀렸다.**

| 지표 | 실패 | 성공 | 판별력 |
|---|---|---|---|
| defect/object 면적비 (median) | 0.041 | 0.014 | 분포가 크게 겹침. 단독 판별 불가 |
| defect 세장비 장축/단축 (median) | 3.83 | 3.40 | 겹침. 판별 불가 |
| **defect bbox 채움률 (median)** | **0.046** | **0.100** | **갈림** |

판별 인자는 defect의 **분산도**다. 실패 소스의 defect는 바운딩 박스의 4.6%만 채운다.
즉 결함 화소가 넓은 영역에 흩어져 있다. 성공 소스는 10%로 두 배 뭉쳐 있다.

흩어진 defect는 얇은 선 두 개로 45%를 덮는 것이 기하학적으로 불가능하다. defect
중심을 기준점으로 잡는데 그 중심이 결함 화소 위에 있지 않을 수도 있다.
게다가 실패 소스의 defect는 면적도 3배 크다. 덮어야 할 양이 많고 흩어져 있다.

**정리하면 `rgb_reflection_glare` 게이트는 결함이 한 덩어리로 뭉친 소스를 전제한다.
흩어진 결함을 가진 소스에서는 재시도·reserve 어느 쪽으로도 회복되지 않는다.**

## 4. `verify`가 미완성 데이터셋을 통과시킨다

548장이 부족한 산출물에 `verify`를 돌린 결과다.

```json
{ "verified": true }
```

exit=0이다. `verify_dataset()`(`generator.py:962`)이 검사하는 것은 행 단위 무결성뿐이다.

- `synthetic_id` 중복
- 출력 stem 중복
- 출력 이미지 SHA-256 중복
- 출력 픽셀 해시 중복
- 각 행의 파일 존재와 내용

**수량과 case 쿼터는 검사하지 않는다.** 그 검사는 `generate()` 본문
(`generator.py:780-832`)에만 있고, 그보다 앞선 777행의
`if errors: raise`에서 먼저 중단되므로 도달하지도 않는다.

결과적으로 이 산출물을 넘겨받아 `verify`로 검수하면 정상으로 오판한다.
`verify`는 "이 데이터셋이 계약대로 완전한가"가 아니라 "각 행이 서로 어긋나지
않는가"만 답한다.

## 5. 조정 가능한 값과 그 대가

실패를 우회하려면 `reserve_per_modality`(현재 500)나
`max_augmentation_retries`(현재 8)를 만지게 된다. 그런데 둘 다
`PERFORMANCE_ONLY_KEYS`에 없다.

```python
PERFORMANCE_ONLY_KEYS = frozenset({
    "checkpoint_interval", "hash_chunk_bytes", "jobs",
    "max_logged_error_examples", "memory_budget_ratio",
    "memory_probe_fallback_jobs", "memory_sample_interval_seconds",
    "parallel_chunk_multiplier", "plan_checkpoint_interval",
    "plan_log_interval", "worker_peak_rss_bytes",
})
```

즉 이 값들을 바꾸면 plan 해시가 바뀌어 **전체 재-plan이 강제된다**(약 20분)
그리고 재생성(약 78분)이 뒤따른다.

`max_augmentation_retries`는 앞서 보인 대로 이 실패 모드에 효과가 없으므로
올릴 이유가 없다. `reserve_per_modality`를 올리는 것은 증상 대응이며, glare
실패율이 33%인 이상 얼마나 올려야 충분한지 보장할 수 없다.

`--resume`도 답이 아니다. 실패한 행은 이미 재시도와 reserve를 모두 소진했고,
소스와 시드가 고정돼 있어 다시 돌려도 같은 결과가 나온다.

## 다음 단계로 검토한 세 방향

근본 해결은 `augment.py`의 `rgb_reflection_glare` 기하 탐색과 품질 게이트에 있다.
흩어진 defect를 가진 소스를 어떻게 다룰지가 정해져야 한다. 방향은 셋이었다.

1. **탐색 공간을 넓힌다** — 기준점을 defect 중심 하나가 아니라 여러 곳으로 잡고,
   길이·폭 계수를 늘린다. 게이트 기준은 그대로 둔다.
2. **게이트를 완화한다** — `minimum_defect_coverage` 0.45를 defect 분산도에 따라
   낮춘다. 다만 이 값은 "반사가 결함을 가려 검출을 방해한다"는 case 정의와 직결되므로
   함부로 낮추면 case의 의미가 흐려진다.
3. **소스 적격 조건을 plan 단계로 올린다** — 현재 planner는 glare에 대해
   `has_battery_outline`만 본다. defect 분산도 조건을 추가해 애초에 덮을 수 있는
   소스만 배정한다. 실패를 생성이 아니라 계획 단계에서 잡는다.

case 정의를 건드리지 않는 1번을 먼저 붙였다. 아래는 그 결과다.

## 6. v2.1 — 탐색 공간 확대

### 설계

확장 탐색은 **좁은 격자가 아무 후보도 못 찾았을 때만** 돈다. 지금 성공하는 소스는
소비하는 난수까지 포함해 출력이 그대로다. 게이트 임계값은 하나도 건드리지 않았으므로,
확장 탐색이 통과시킨 후보도 좁은 격자가 통과시킨 후보와 같은 계약을 만족한다.

확장한 축은 셋이다.

- **조준점** — defect 전체 중심 하나가 아니라, defect 화소를 자기 주축 방향으로
  같은 개수씩 나눠 각 구간의 medoid를 쓴다(`_defect_anchors`). 각 앵커는 실제 결함
  화소에 스냅된다. 흩어진 defect는 전체 중심이 결함 화소 위에 없을 수 있다.
- **두 획의 간격** — 좁은 격자는 간격이 `width * 1.8`로 고정이라 두 획이 붙어
  사실상 굵은 선 하나다. `(1.8, 6.0, 14.0)`으로 벌려 흩어진 defect를 걸치게 했다.
- **길이·폭 계수** — 짧고 얇은 쪽을 추가해(`0.22~0.80`, `0.7~1.8`) outline 밖으로
  잘려나가 면적을 잃는 경우를 줄였다.

**획 개수는 레버가 아니다.** 별도 파라미터 게이트가 `len(patches) != 2`로 두 개를
강제한다. 처음에 1개도 허용했다가 `quality_gate: glare parameters are outside
v1.9 range`로 걸렸다.

### 성능

확장 격자를 원본 프레임(1920×1080)에 매번 래스터화했더니 **소스당 20초를 넘겼다.**
두 가지로 줄였다.

- 점수 계산은 획의 밝기와 무관하므로, 셀 바운딩 박스로 자른 **이진 캔버스**에서
  후보를 훑는다. 이긴 후보 하나만 기존 경로로 다시 렌더한다.
- 클리핑은 면적을 줄이기만 하므로, 자르기 전 면적이 이미 4.5%에 못 미치는 후보는
  래스터화 전에 건너뛴다.

| 구현 | 소스당 시간 |
|---|---|
| 확장 격자를 풀 프레임에 래스터화 | 20초 초과 |
| 이진 캔버스 + 사전 가지치기 | 약 1.8초 |

연결성분 라벨링도 시도했다가 뺐다. 순수 파이썬 flood fill은 소스당 수 초가 걸렸고,
numpy 라벨 전파로 바꿨더니 성분 지름만큼 반복해 더 느렸다. 조준점은 픽셀 정확도가
필요 없으므로 분위수 구간 medoid로 충분하다.

### 결과

실패 소스 20건을 그대로 재현했다.

| 구분 | 결과 |
|---|---|
| 회복 | 12건 |
| 여전히 `glare_no_gate_safe_geometry` | 8건 |
| **회복률** | **60%** |

간격을 `(1.8, 4.0, 8.0, 14.0, 22.0, 34.0)`까지 늘려봤지만 회복은 12건 그대로였고
소스당 시간만 1.8초에서 2.5초로 늘었다. 되돌렸다.

### 남은 40%는 탐색 문제가 아니다

회복되지 않은 8건을 따로 쟀다. `core_ratio` 상한인 object 면적의 12%를 defect
영역에 통째로 얹었을 때 닿을 수 있는 defect 비율(밀도 기준 상한)을 요구
커버리지와 비교했다.

| synthetic_id | defect/object | 요구 커버리지 | bbox 채움률 | 밀도 기준 도달 상한 |
|---|---:|---:|---:|---:|
| `QF20_RGB_00006628` | 0.1457 | 0.450 | 0.170 | 0.14 |
| `QF20_RGB_00006764` | 0.0487 | 0.450 | 0.045 | 0.11 |
| `QF20_RGB_00006921` | 0.0593 | 0.450 | 0.055 | 0.11 |
| `QF20_RGB_00007092` | 0.0124 | 0.450 | 0.015 | 0.15 |
| `QF20_RGB_00007273` | 0.0061 | 0.450 | 0.007 | 0.14 |

8건 전부 도달 상한이 요구치에 미치지 못한다. `QF20_RGB_00007273`은 bbox 채움률이
0.007이다. 결함이 흩뿌려진 점들이라 어떤 배치로도 45%를 덮을 수 없다.

**즉 60%가 탐색 확장의 천장이다.** 남은 소스는 두 획으로 defect의 45%를 덮으면서
core를 object의 12% 안에 두는 것이 기하학적으로 불가능하다. 여기서 더 가려면
2번(게이트 완화)이나 3번(계획 단계 적격 조건)으로 넘어가야 하고, 둘 다 case 정의에
닿으므로 데이터 담당과 합의가 필요하다.

다만 실패 수가 줄면 reserve(모달리티당 500)가 흡수할 여지가 생긴다. v2.0에서는
최종 미충족이 548건이라 500개 풀로 못 메웠다.

## 7. 확장 탐색이 만든 2차 문제 — 실패 경로 비용 폭증

확장 탐색을 붙인 뒤 첫 재생성은 CT 20,000장을 끝내고 RGB로 넘어간 직후 진척이
멎었다. 25분 동안 `dataset_manifest.csv`가 갱신되지 않는데 워커 6개는 계속 CPU를
쓰고 있었다.

원인은 **무의미한 반복 두 곳에 비싼 탐색이 곱해진 것**이다.

**재시도 8회.** §3에서 이미 확인했듯 `*_no_gate_safe_*` 실패는 시드와 무관하다.
`glare`뿐 아니라 `uneven_lighting`(각도 4개 × 게인 3쌍 전량 시도, rng는 각도 순서만
회전)과 `alignment_crop`(이분탐색)도 마찬가지로 고정 격자 전수 탐색이다. 확장 탐색을
붙이면서 이 8회 반복을 그대로 뒀더니, 무의미한 반복 하나하나가 비싸졌다.

**reserve 전수 순회.** 더 컸다. 실패한 reserve는 `consumed_source_keys`에 들어가지
않으므로, 이후 실패 행마다 죽은 reserve 500개를 처음부터 다시 시도했다. 각 시도가
이미지·JSON SHA-256 + 전체 증강이다. 실패 190건 × reserve 500개면 95,000회다.

### 조치

- `ExhaustedSearchError`를 도입해 전수 탐색 실패는 재시도하지 않는다. 게이트 실패는
  파라미터가 시드에 따라 달라지므로 8회 재시도를 그대로 둔다.
- reserve가 어떤 case에서 탐색을 소진하면 `(소스, failure_case)`로 기억해 다시
  방문하지 않는다.
- 한 샘플이 시도할 reserve 수에 상한을 둔다(`RESERVE_ATTEMPTS_PER_SAMPLE = 40`).
  튜닝 값이 아니라 안전 한계이므로 config가 아닌 모듈 상수로 뒀다. config에 넣으면
  plan 해시가 바뀌어 재-plan이 강제된다.

워커 예외는 프로세스 경계를 넘으며 문자열로 뭉개지므로, generator는 예외 타입이
아니라 공유 마커 상수(`EXHAUSTED_SEARCH_MARKER`)로 이 부류를 판별한다.

실패 1건 비용을 실측했다. **3.4초 → 0.42초.**

### 성급하게 죽인 실행에 대해

첫 재생성을 "정지"로 판단해 중단했는데, 그 판단은 근거가 부족했다. 두 번째 실행에서
같은 지점(19,976 = CT/RGB 경계)에 9분간 카운터가 멈췄을 때 산출물을 직접 세어 보니
**RGB 이미지가 이미 5,332장 만들어져 있었다.**

`executor.map`은 결과를 plan 순서대로 돌려준다. chunk 크기가
`40,000 / (6 × 8) = 833`이라, 경계 청크를 맡은 워커가 끝날 때까지 카운터가 멈춰
보인다. 그 사이 다른 워커들은 계속 생산한다. RGB는 1920×1080이라 CT 크롭보다
훨씬 느려서 첫 RGB 청크가 오래 걸린다.

**진척 판정은 진행 로그가 아니라 산출물 파일 수로 해야 한다.** 첫 실행도 같은
현상이었을 가능성이 있다. 다만 위 조치 자체는 실측으로 뒷받침되므로 헛수고는 아니다.
