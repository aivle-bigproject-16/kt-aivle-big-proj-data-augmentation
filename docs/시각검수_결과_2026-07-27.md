## 탈락 1 — rgb_uneven_lighting (63.33%)

거부 사유(검수자 기록): **"밝기가 균등하게 밝음"** — 조명 기울기를 육안으로 식별할 수 없음.

### 수치

거부/승인 각 이미지의 밝기 비대칭도를 게이트와 동일한 정의로 측정했다
(`augment.py:722-732`, 좌우·상하 절반 평균 휘도 차 ÷ 전체 평균 휘도).

| 판정 | 장수 | 최소 | 중앙값 | 최대 |
|---|---:|---:|---:|---:|
| 승인 | 19 | 12.8% | **35.1%** | 56.1% |
| 거부 | 11 | 12.2% | **17.8%** | 33.0% |

거부분 분포: 12, 13, 13, 15, 16, 18, 19, 24, 28, 29, 33 (%)
승인분 분포: 13, 21, 21, 25, 26, 27, 30, 31, 33, 35, 36, 38, 40, 41, 41, 45, 48, 49, 56 (%)

### 원인

현재 게이트 기준은 **0.12(12%)** 로, 거부분 중앙값 17.8%보다도 낮다. 즉 기준을 통과했으나
사람 눈에는 조명 불균일로 보이지 않는 이미지가 다수 생성됐다.

### 수정 제안

1. `quality_gate`의 임계값을 **0.12 → 0.25~0.30** 으로 상향. 거부분 11장 중 8장이
   25% 미만이므로 대부분 차단된다.
2. 다만 **13~33% 구간에서 승인·거부가 겹친다.** 승인 최소는 12.8%, 거부 최대는 33.0%로,
   밝기 수치만으로 완전히 분리되지 않는다. 임계값 상향만으로는 재발 가능성이 남는다.
3. 겹침의 원인으로 의심되는 것: 현재 측정은 **프레임 전체** 기준이라, 배터리가 프레임
   중앙의 좁은 영역만 차지할 때 배경에는 기울기가 있어도 **배터리 자체는 균일하게**
   보인다. 측정 범위를 outline mask 영역으로 한정하는 방식을 검토할 것.

## 탈락 2 — rgb_trigger_timing_failure (76.67%)

거부 사유(검수자 기록):
**"배터리가 프레임 안에 온전히 담겨 정상 촬영 사진과 구별되지 않음"**

### 수치

출력 긴 변이 512로 고정되므로, **짧은 변이 작을수록 많이 잘린 것**이다.

| 판정 | 장수 | 최소 | 중앙값 | 최대 |
|---|---:|---:|---:|---:|
| 승인 | 23 | 179 | 243 | 447 |
| 거부 | 7 | **321** | **333** | **346** |

승인분 짧은 변 분포:
`179, 180, 180, 199, 203, 207, 208, 213, 215, 222, 236, 243, 243, 248, 250, 251, 251, 387, 396, 398, 400, 440, 447`

### 원인

**크롭 양의 문제가 아니다.** 거부된 7장은 321~346의 좁은 구간에 몰려 있지만, 승인분
중에도 387~447처럼 **더 적게 잘린 이미지가 6장** 있다. 크롭 양만으로는 승인/거부가
분리되지 않는다.

실제 원인은 **크롭 방향과 배터리 위치의 관계**다. `timing_edge_crop`은 상·하·좌·우 중
한 변을 랜덤으로 골라 10~38%를 잘라낸다(`augment.py:367-384`). 배터리가 프레임 중앙에
있고 잘라낸 쪽이 배경뿐이면, **배경만 사라지고 배터리는 온전히 남는다.** 결과 이미지는
정상 촬영 사진과 구별되지 않는다.

현재 게이트는 이를 막지 못한다. outline retention 검사는 **하한만** 있다:

```python
# augment.py:784-794
minimum = 0.50 if "timing_edge_crop" in record_types else ...
if retained < minimum:
    raise ValueError("quality_gate: outline retention ... is below ...")
```

`retained = 1.00`(배터리가 전혀 잘리지 않음)도 통과한다.

### 수정 제안

1. **retention 상한 추가**가 가장 직접적이다. `timing_edge_crop`에 대해
   `retained > 0.90`이면 게이트 실패로 처리해, 배터리가 실질적으로 잘리지 않은 결과를
   차단한다.
2. 또는 크롭 방향을 랜덤이 아니라 **배터리 bounding box 기준으로 선택**해, 자르는 변이
   반드시 배터리와 겹치도록 한다. 이 방식이 재시도 횟수를 줄인다.
3. 두 방법 모두 하한 0.50과 함께 쓰면 "너무 많이도, 너무 적게도 잘리지 않은" 구간으로
   결과가 수렴한다.

## 검수 도구

`index.html`은 정적 뷰어여서 검수자가 CSV를 직접 편집해야 했다. 510행을 손으로 채우면
행 밀림·오타로 `_visual_qa_gate`의 `synthetic_id` 집합 대조가 실패한다. 이번 검수를 위해
판정 입력형 도구를 만들어 사용했다.

| 파일 | 용도 |
|---|---|
| `review_tool.html` | 판정 입력 도구. 키보드 판정, 대비 4단계·확대, 케이스 필터, 승인율 실시간 표시, 자동 저장. 내보낼 때 원본 행 순서·ID를 그대로 유지한다 |
| `merge_and_check.py` | 검수자별 CSV 병합 + 게이트 사전 판정. 헤더·ID 세트 대조, `approved` 허용값 검사, 판정 충돌 검출, 케이스별 승인율 계산 |
| `참고_CT_8케이스.png` / `참고_RGB_9케이스.png` | 케이스별 대표 샘플 |

`merge_and_check.py` 종료 코드: `0` 통과 / `1` 95% 미달 / `2` 검수 미완료

### CT 검수 시 유의점

CT 출력은 53×512 등 가늘고 어두워, 원본 대비로는 ring·stripe 아티팩트가 육안으로
식별되지 않는다. 검수 도구에 대비 보정(4단계)과 확대를 넣은 이유다. 향후 검수에서도
**대비를 최소 한 단계 올린 상태로 판정**할 것을 권한다.

## 남은 조치

1. `rgb_uneven_lighting`, `rgb_trigger_timing_failure` 두 case의 파라미터·게이트 수정
2. 해당 case **전체 재생성** (계획서 v1.5 §7.3)
3. 재생성분에 대해 두 case만 재검수 (각 30장)
4. 전 case 95% 이상 확인 후 `fail_visual_qa.csv` 반영 → `-Stage resume`

`fail_visual_qa.filled.csv`의 나머지 15개 case 판정은 재사용 가능하다. 다만 재생성 시
`synthetic_id`가 바뀌면 QA 선택도 다시 산출되므로, **재생성 범위를 해당 case로 한정**해야
기존 판정을 살릴 수 있다.

## 인코딩 주의

`fail_visual_qa.csv` 계열은 파이프라인이 `utf-8-sig`(BOM 포함)로 읽고 쓴다
(`generator.py:99, 108`). BOM 없이 저장하면 한글 Windows의 Excel이 CP949로 해석해
`reviewer`·`reason`의 한글이 깨진다. Excel에서 편집 후 저장하면 CP949로 되돌아가므로,
**CSV는 도구나 스크립트로만 수정할 것.**
