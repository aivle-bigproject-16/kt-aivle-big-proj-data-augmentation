# 작업 노트 — 2026-07-24

이 문서는 2026-07-24에 `quality-fail-augment` 저장소에 적용한 변경 사항을 팀원이 읽을 수
있도록 정리한 것이다. 목표는 40k CT/RGB PASS/FAIL 데이터셋 생성 파이프라인을 실제 원본
데이터로 처음부터 끝까지 돌리는 것이었고, 그 과정에서 발견한 병목과 결함을 함께 수정했다.

## 성능·안정성 변경 상세

### 1. 원본 scan 병렬화 (`planner.py`)

`scan()`의 쌍별 검증(이미지 디코드, SHA-256 3종, CT porosity)이 단일 스레드로 약 27.6만 쌍을
처리해 1회에 약 6시간이 걸렸다. 이 검증만 `ProcessPoolExecutor`로 `jobs` 수만큼 병렬화하고,
순서에 의존하는 병합(픽셀 중복 제거, 계통 오류 누적, 감사 순서)은 정렬 순서대로 메인에서 직렬
수행한다. 따라서 raw fingerprint는 병렬·직렬 산출이 동일하다. 미사용 label 딕셔너리는 워커에서
비워 프로세스 간 전송 비용을 줄였다.

### 2. `--trust-plan` 빠른 경로 (`generator.py`, `cli.py`)

`generate`는 매 호출마다 `_validate_plan`에서 전체 원본을 다시 스캔해 fingerprint를 재대조했다.
plan 직후처럼 원본 불변이 확실할 때 `--trust-plan`을 주면 이 전체 재스캔을 생략한다. 이때도 plan이
사용하는 40k + reserve 소스는 각각 SHA-256으로 검증하므로 선택된 소스의 무결성은 유지된다.
기본값은 안전한 전체 재스캔이며, 플래그를 줄 때만 생략한다.

### 3. 체크포인트 게이팅 + `verify_dataset` 병렬화 (`generator.py`)

- 매 샘플마다 매니페스트 CSV 3종을 통째로 다시 쓰던 것을 `checkpoint_interval`(기본 25)마다만
  쓰도록 바꾸고, 생성 종료 후 최종 flush를 추가했다. 기존 방식은 40k 생성에서 O(n^2)이라, 워커가
  이미 대부분의 이미지를 만든 뒤에도 메인이 약 8샘플/초로 기록만 기어갔다.
- `verify_dataset`의 샘플별 검증(디코드·해시·polygon·라벨·이력)을 워커로 분산하고, 4종 중복 집합은
  row 순서대로 메인에서 직렬 병합한다. 유효 데이터셋은 병렬·직렬 검증 결과가 동일하다.

### 4. `atomic_write` 재시도 (`common.py`)

40k 생성이 45% 지점에서 `PermissionError [WinError 5]`로 중단된 적이 있다. `os.replace`가 매니페스트
파일을 다른 프로세스(진행 상황을 확인하는 리더, 안티바이러스, 검색 인덱서)가 잠깐 열고 있을 때
실패한 것이다. `os.replace`는 성공하면 원자적이므로, 지수 백오프로 재시도하도록 바꿔 일시적
공유 위반으로 전체 실행이 죽지 않게 했다.

> 운영 주의: 생성이 도는 동안 `manifests/*.csv`를 열어 읽지 말 것. Windows에서 리더가 파일을
> 잡고 있으면 위 경합을 유발한다. 진행 상황은 `pipeline.status`와 `logs/`로만 확인한다.

### 5. `duplicate_pixel_hash` 계통 오류 면제 (`planner.py`)

원본에 픽셀이 동일한 RGB 이미지가 다수 있어, 정렬 순서상 중복 제외가 20건 연속되면 "계통 스키마
오류"로 plan 전체가 중단됐다. 픽셀 중복 제거는 의도된 정상 제외이므로 CT porosity 제외와 동일하게
계통 오류 카운터에서 면제했다. 중복은 여전히 제외되며 plan은 계속 진행된다.

## 품질 변경 상세 — augmentation 게이트 실패 3종

전 케이스(17개)에 대해 plan의 fail 배정 소스로 실패율을 측정한 결과, 세 케이스가 실린더 셀에서
품질 게이트를 통과하지 못했다(나머지 14개는 0%). 게이트 기준(계약 정의)은 낮추지 않고 생성
로직을 고쳐 모두 0%로 만들었다.

- `rgb_reflection_glare`: 반사 패치를 프레임 기준으로 크게(최대 폭·높이의 1/4) 잡고 외곽선의
  아무 점에나 중심을 두어, 작은 실린더 외곽선을 벗어나 "외곽선 겹침 70% 미만"으로 65% 실패했다.
  패치 크기를 마스크 자체 범위의 일부로 제한하고 중심을 마스크 중심 쪽으로 당겨 0%로 낮췄다.
- `ct_low_resolution`: 다운스케일 배율이 랜덤이라 CT 소스마다 다른 엣지 손실을 내, "엣지 70% 초과
  손실"로 86% 실패했다. 배율을 랜덤으로 뽑는 대신 게이트 범위 안의 목표 비율을 향해 이진 탐색해
  결과가 항상 [0.30, 0.80] 안에 들도록 바꿔 0%로 낮췄다.

### hair contamination

`rgb_hair_contamination`은 배터리 외곽선 내부의 한 점에서 머리카락을 시작해 임의 방향으로
장변의 0.35~0.90 길이만큼 뻗었다. 품질 게이트는 머리카락 샘플점의 50% 이상이 외곽선 마스크 안에
있을 것을 요구한다. 그런데 실린더 셀은 프레임의 약 11%만 차지해(마스크 대각이 장변의 약
0.35~0.6) 긴 머리카락이 대부분 마스크 밖으로 나가 게이트를 통과하지 못했다.

- 측정: 40k plan의 hair 배정 원본 160장(전부 실린더)에서 **87%(139/160)가 8회 재시도를 모두
  소진해 실패**했다. reserve 소스도 실린더라 대체 역시 실패하므로, 그대로 두면 RGB reserve 500이
  고갈되어 전체 실행이 실패했을 것이다.
- 수정: 머리카락을 마스크 점들의 주축(PCA)에 맞춰 정렬하고 마스크 중심에 배치하며, 길이를 내부
  범위의 1.5배 이하로 제한하되 0.35~0.90 장변 길이 게이트는 유지한다. 그러면 교차 비율이
  구조적으로 0.5를 넘는다.
- 재측정: 같은 160장에서 **실패 0건**.

## 자동 파이프라인 — `run_pipeline.ps1`

개별 CLI 명령을 하나의 진입점으로 묶은 PowerShell 7 스크립트다. 스테이지는 `plan`, `smoke`,
`generate`, `resume`, `verify`, `upload`이며, 실행 유지(keep-awake), `-Detached` 분리 실행,
`<Output>-pipeline\pipeline.status` 하트비트, 단계별 로그를 지원한다. 상세 사용법은 README의
"자동 파이프라인" 절을 참고한다.

- 두 단계 RSS 측정: `smoke`가 `worker_peak_rss_bytes`를 측정해 `config.40k.measured.json`을
  자동 생성한다. 이 config로 plan을 다시 만들면 이후 full 생성이 병렬 worker로 돈다.
- 사람 visual-QA 게이트: `generate`가 끝나면 `exit=10`으로 멈추며, 사람이 510장을 검토해
  `manifests\fail_visual_qa.csv`의 `reviewer`와 `approved`를 채워야 `resume`가 통과한다.
  스크립트는 이 검토를 자동으로 통과하지 않는다.

## 실측 소요 시간 (이 머신 기준)

| 단계 | 시간 |
|---|---|
| plan (병렬 scan 포함) | 약 50~66분 |
| smoke (전체 재스캔 포함) | 약 53분 |
| smoke (`--trust-plan`) | 약 3분 |
| full generate (`--trust-plan`, 40k 병렬) | 검증 약 2분 + 생성 진행 |
| resume | verify 2회 + ZIP + summary |
| upload | rclone 전송, 데이터 크기·업링크 의존 |

## 남은 알려진 항목

- 재-plan은 measured config가 `config_sha256`만 바꾸기 때문에 선택 결과가 동일한데도 강제된다.
  없애려면 `config_sha256`에서 성능 전용 키(`worker_peak_rss_bytes` 등)를 제외하는 계약 수정이
  필요하다. 현재는 병렬 생성으로 얻는 이득이 커서 그대로 둔다.
- CT 실패 케이스(augmentation retries exhausted)는 약 1% 수준으로, reserve로 정상 대체된다.
